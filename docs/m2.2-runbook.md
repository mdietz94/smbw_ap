# M2.2 — 10-Coin routing runbook

Last updated: 2026-05-25.

## TL;DR

**The hunt is over before it started.** M2.2 needs no new Switch-side
hook. The `course_result` PlayReport already carries
`big_flower_coin_course_in` and `big_flower_coin_course_out` — each a
`bool[3]` describing the state of the 3 named "Big Flower Coin" / 10-coin
placements per course at entry vs exit. **Diff = newly-collected this
run**, which is exactly what the apworld's `"<course> - 10 Coin #1/#2/#3"`
locations want.

**Status (2026-05-25)** — ✅ **bridge implementation shipped.** ~30 LoC of
real change across [bridge/processor.py](../bridge/processor.py),
[bridge/protocol.py](../bridge/protocol.py),
[bridge/state.py](../bridge/state.py), and
[bridge/location_table.py](../bridge/location_table.py); +21 new tests
(224 total in the bridge suite, up from 203, all green).  Routable
locations are gated on the `_TEN_COIN_TABLE` entries that map
`(stage_key, coin_index) → AP location name` — currently W1-1 and W1-2
(palaces intentionally absent — they have no 10-coin placements).
**The one blocking risk** (diff-semantics interpretation) and **the
backlog** (98 remaining course stage_keys to map; tracked as task #7 in
this session's task list) remain — see below.

## Why the original Ghidra hunt is moot

The milestone plan ([docs/milestones.md](milestones.md) M2.2) and risk
register described two parallel hunt paths for 10-coin event detection:

1. **Find a `RequestEventGetBigTenLuckyCoin` Nerve**, add a vtable filter
   to `NerveActivateOnce` like Wonder Seed.
2. **Fallback**: hook the coin-counter writer at NSO `+0x49253C` (from
   HamletDuFromage's cheat DB) with a value-filter (+10 vs +1 vs +50).

Both paths solve the *event-detection* problem but **leave the identity
problem unsolved** — i.e., "*which* of the 3 coins in this course did
the player just collect?". The Nerve-hunt path would have required
follow-up RE to extract the placement-hash from the actor pointer, same
as the deferred Wonder Seed multi-seed problem.

The PlayReport path **solves both problems at once** — event detection
*and* per-coin identity — for free.

## What the corpus tells us

From decoding the 4 captured `course_result` fixtures
([bridge/test_play_report.py](../bridge/test_play_report.py)):

| Fixture | `big_flower_coin_course_in` | `_out` | `flower_coin_course_in→out` | `get_lucky_coin` |
|---|---|---|---|---|
| W1-1 Top-of-Flag | `[T,T,T]` | `[T,T,T]` | 135 → 135 (Δ=0) | 0 |
| W1-2 Secret-Exit | `[F,T,T]` | `[F,T,T]` | 135 → 146 (Δ=11) | 11 |
| Palace WIN (companion course_result) | `[F,F,F]` | `[F,F,F]` | 146 → 148 (Δ=2) | 2 |

Three confirmed structural facts:

1. **`flower_coin_course_out − _in == get_lucky_coin`** in every fixture.
   So `flower_coin` (running purple-coin total, container-A hash
   `0xf4ee6827`) and `get_lucky_coin` (per-run purple-coin delta) are
   the same quantity at different timescales.
2. **`big_flower_coin_*` is bool[3] for the 3 NAMED `ObjectBigTenLuckyCoin`
   placements per course** — not the general purple-coin total. Confirmed
   by:
   - Palace WIN run shows `[F,F,F]` for `big_flower_coin_*` despite
     `get_lucky_coin=2` (the 2 purple coins came from non-named
     sources — block hits, enemy drops, etc.); palaces don't have the
     3 named placements.
   - W1-2 Secret-Exit shows `[F,T,T]` carry-over from prior runs while
     `get_lucky_coin=11` came from off-named sources.
3. **None of our captures show `_in != _out`**, so the "diff = collected
   this run" interpretation is INFERRED from the field naming (`_in` vs
   `_out`) but not yet PROVEN. See [Empirical verification](#empirical-verification).

## Bridge-side implementation plan

Five surgical changes — pure bridge code, no Switch-side or RE work.

### 1. New CheckKind in [bridge/protocol.py](../bridge/protocol.py)

```python
class CheckKind(str, Enum):
    ...
    TEN_COIN = "ten_coin"               # 306 AP checks (102 courses × 3)
```

The `CheckEmitted.metadata` dict gains `coin_index: 0|1|2` for routing.

### 2. New emit in [bridge/processor.py](../bridge/processor.py) `_handle_course_result`

After the existing exit-type emit, before returning, diff
`big_flower_coin_course_in` vs `_out`:

```python
in_arr = fields.get("big_flower_coin_course_in") or []
out_arr = fields.get("big_flower_coin_course_out") or []
for idx in range(min(len(in_arr), len(out_arr))):
    if out_arr[idx] and not in_arr[idx]:
        emit_check(CheckEmitted(
            kind=CheckKind.TEN_COIN,
            stage_key=stage_info["stage_key"],
            metadata={..., "coin_index": idx},
        ))
```

The palace `course_result` companion is already suppressed by the
`world_mother_seed` early-return, so palace WINs don't accidentally
emit 10-coin checks.

### 3. Location-name lookup in [bridge/location_table.py](../bridge/location_table.py)

The existing `_TABLE: dict[(CheckKind, stage_key), str]` doesn't carry
the per-coin index. Two viable shapes:

- **Option A** (uniform): change the key to `(CheckKind, stage_key,
  index)` with `index=0` default for non-coin kinds. Touches every
  existing entry.
- **Option B** (separate table): add a sibling
  `_TEN_COIN_TABLE: dict[(stage_key, index), str]` and a special-case
  lookup branch. Less churn.

Recommended: **Option B**, given only TEN_COIN has the third axis.

Each entry of the 10-coin table looks like:

```python
(_STAGE_W1_1, 0): "W1: Welcome to the Flower Kingdom! - 10 Coin #1",
(_STAGE_W1_1, 1): "W1: Welcome to the Flower Kingdom! - 10 Coin #2",
(_STAGE_W1_1, 2): "W1: Welcome to the Flower Kingdom! - 10 Coin #3",
```

### 4. The 102-course stage_key map

The bridge currently has 3 stage_keys captured (W1-1, W1-2, Pipe-Rock
Palace). The 99 remaining non-palace W1+W2+...+W6 course stage_keys
must be captured incrementally. Each entry costs **one course visit**
(observe the `course_in` PlayReport's `stage_info.stage_key`).

This is **the same backlog M2.6 / location_table.py already has** for
WONDER_SEED / NORMAL_EXIT / TOP_OF_FLAG. Adding 10-coin doesn't make
the backlog longer — it adds 3 entries per already-mapped course.

Practical sequence: do a fresh-save full playthrough with the bridge
logging every `course_in` stage_key (already happens). Each course adds
1 + up to 7 location-table entries (3 for 10-coin, 1 each for
normal/secret/top-of-flag/wonder-seed/fake/palace as applicable).

### 5. Tests in [bridge/test_processor.py](../bridge/test_processor.py)

- Synthetic `course_result` with `big_flower_coin_course_in=[F,F,F]`,
  `_out=[T,F,F]` → expect 1 emit with `coin_index=0`.
- Same with `_in=[T,F,F]`, `_out=[T,T,T]` → expect 2 emits with
  `coin_index ∈ {1, 2}`.
- Palace WIN companion (`world_mother_seed=True`) → expect 0
  TEN_COIN emits even if `big_flower_coin_*` had values.
- `big_flower_coin_*` missing entirely → no emit, no crash.

## Open question: array index vs apworld # numbering

The apworld names 10-Coin locations `#1` / `#2` / `#3`. The PlayReport
array indices 0 / 1 / 2 are some internal ordering (probably the
in-level placement order baked into the level data). **Whether
`array_index == 0 maps to apworld #1` is unknown.**

Two responses:

- **Blind mapping (recommended MVP)**: ship `index N → "#<N+1>"`.
  Correctness for player progress is unaffected — they still get credit
  for 3 distinct AP locations as they collect all 3 in-game coins. The
  *only* downside is that the AP location name shown in the log might
  not match the physical coin position the player picked up. Cosmetic.
- **Empirical mapping (deferred)**: collect each per-course `#1`/`#2`/`#3`
  in isolation, observe which array index flips, build a 102×3 lookup.
  Order-of-magnitude more capture work. Defer until/unless a bug
  report forces the issue.

## Empirical verification

The diff-semantics interpretation (`_out[i] AND NOT _in[i]` = collected
this run) is unproven by the existing corpus. Verify with ONE capture:

1. Start with the existing playthrough save (W1-1 already has
   `[T,T,T]`; pick a course where at least one 10-coin is still
   `False`). W1-2's `[F,T,T]` works.
2. Enter W1-2, collect the missing coin (#1 in the array), do a flag
   touch.
3. Wait for the post-save `prepo.ipc.bytes(...)` log lines for the
   `course_result` event.
4. Paste into a new test fixture `W1_2_COURSE_RESULT_COLLECTED_ONE`
   that asserts `_in == [F,T,T]` AND `_out == [T,T,T]`.

If `_in[0]` was indeed False and `_out[0]` is now True after collecting
the missing coin, the diff semantics is locked in. If not, the entire
plan needs rethinking — likely fall back to the Nerve-hunt path.

This is the **only blocking risk** in the entire plan.

## Why the deferred-write caveat does NOT apply

Container A counter grants and container B bool grants have a
save-survival caveat (the dirty buffer flushes on next save; load-fresh
reverts). 10-coin routing is **outgoing only** (AP-check emission) —
we're not writing anything to the game's save state. The
`course_result` PlayReport is emitted by the game *during the
save-after-clear path*, so its `_out` snapshot is already in the
persistent state by the time we see it.

The Switch never receives a 10-coin item from AP (10-coins aren't AP
items in the manual world — they're location checks only), so no replay-on-
HelloMsg or absolute-overwrite pattern is needed for this path.

## Where this leaves the M2.2 milestone

| Aspect | Original plan | Revised plan |
|---|---|---|
| Switch-side hook | New Nerve filter on `RequestEventGetBigTenLuckyCoin` | None — reuse M2.4 |
| Identity extraction | New: read placement hash from nerve struct (Ghidra) | None — array index from PlayReport |
| Fallback path | Counter-write hook at NSO +0x49253C with value-filter | Same, retained for post-MVP if PlayReport diff fails verification |
| Bridge changes | New per-course `placement_hash → "#N"` table (manual mapping) | New `(stage_key, index) → "#N"` table; blind index mapping for MVP |
| Risk profile | Medium (RE on nerve struct layout, then field-name hash) | Low (one fixture capture to verify diff semantics) |
| Effort estimate | "1–2 sessions" | Half a session for impl + tests; one play session for the stage_key map fill-out |

## Not in scope here

- The 102 `stage_key → course_name` entries (this is the
  location_table.py incremental fill-out backlog and applies to all
  CheckKinds equally).
- Per-coin position mapping (apworld `#1/#2/#3` vs array `0/1/2`) —
  deferred; blind mapping is correct-enough.
- The `get_lucky_coin` / `flower_coin_course_*` deltas are noise for
  M2.2's purposes — those represent purple coins from non-named-coin
  sources (?-blocks, enemies, etc.) which don't correspond to AP
  locations.
